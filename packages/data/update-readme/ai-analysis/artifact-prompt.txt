## Task

## Using the inputs
- Tool context describes what each competing configuration is and does. Use it to explain configuration differences. Do not use it to explain performance: implementation language does not establish why a measured result occurred.
- Measured results are the only authority for performance and ranking claims. Cite only values present in the results.
- `gzipReduction` compares minzipped size against the original artifact's gzipped size. `speedVsFastest` compares each configuration with this artifact's fastest one and names that baseline — use it instead of deriving speed ratios yourself.
- A FAILED entry means that exact configuration did not complete this artifact successfully. Describe failures only as recorded: timeout, or the given stage and message. If the stage is "(unknown)", say the failure stage was not recorded rather than guessing what happened. Never invent a cause, and never extend a failure to a tool's other configurations.

## Writing rules
- Two to three sentences. State the balance winner, the most meaningful size or speed trade-off, and any recorded failure.
- Clear, lightly engaging prose. No emojis, no headings, no lists.
- Do not refer to other artifacts, rankings across artifacts, or the benchmark as a whole: you only know this artifact.
- No claims about a tool's history, popularity, authorship, or release quality.
- Do not attribute any result to a tool's implementation language or origin.
- Never claim something is unique ("the only", "the first") — you cannot know that from one artifact.
- Describe times as measured averages, not exact guarantees. Conversions of supplied figures are fine (e.g. "about 0.8 MB"). Use approximate language for close comparisons.
